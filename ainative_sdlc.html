What is this?

The problem: AI coding assistants sometimes say “done” while the tests are still failing.

The fix: AI-Native SDLC (Software Development Life Cycle) adds checks that run automatically inside the AI tool, plus two decisions that stay with a person: approve the plan, and approve the release.

Who it is for: anyone building software with Claude Code or Codex.

01 / The lifecycle

The whole process in five steps

Use this as the short version when teaching the framework.

01 · YOU

Describe the outcome

Say what should change. The AI asks for missing decisions and writes a plan.

02 · PLAN

Check the plan

Requirements, design and proof are recorded. A reviewer looks for gaps.

03 · BUILD

Build on a branch

Tests lead the code. Each change passes the project’s checks.

04 · VERIFY

Prove it works

Fresh eyes run the full suite and review the result. Web apps may get a browser walkthrough.

05 · YOU

Try it, then ship

Test the local result. Send findings as one batch. Release when ready.

One rule to remember: “Done” needs current evidence: passing checks, relevant tests and a change you can inspect. The automatic checks only run once you have approved them in the AI tool and set up the project.
02 / Your role

The decisions that stay with you

The AI handles routine execution. Your judgment sets direction and release timing.

GATE 1

Approve the plan

Is this the right thing to build? Review the short digest and the choices that matter.

YOUR TEST SESSION

Try the local version

Use it as a customer would. Collect screenshots and one-line findings in a single batch.

GATE 2

Choose when to ship

Review the branch, test evidence and release effect. Where push triggers deployment, shipping reaches users.

03 / Evidence

What “verified” means

✓

Fast check

make check catches immediate problems before a commit. If a check cannot run, it says no instead of quietly saying yes.

↗

Full test

make test exercises the project’s behavior before release. The result must be current for the code being shipped.

◎

Independent look

A reviewer checks assumptions and gaps. For a web app, a browser walkthrough adds user-facing evidence.

Commands and when to use them

These seven commands belong to Claude Code. Codex uses its own skills and plain-language requests.

CommandUse it for
/feature <idea>Plan and build a new feature through review.
/spec <idea>Plan only, without changing code.
/buildBuild work already approved; it does not publish.
/shipReview release decisions, merge, re-check and push.
/rca <bug>Reproduce a known bug, fix its cause and protect against recurrence.
/huntSearch for unknown bugs on its own, record findings and stop with a reason; it never publishes.
/test-auditCheck whether the test suite still proves meaningful behavior.

Remember: check is the fast lane: syntax and lint; test runs the tests you already have; /hunt looks for gaps those tests miss. In short: hunt looks for bugs, test-audit judges the tests, rca kills the class of one known bug.

Roles, models and gates

The crew

The roles below describe jobs. Which AI model fills each role is set in the tool’s engine map. The map records the model you asked for; it cannot prove which model is actually running.

RoleJob
JUDGEPlans and makes decisions in the main session.
BUILDImplements approved work with tests.
VERIFYReviews plans and checks finished work.
READResearches and gathers evidence.
HOOKSMechanical checks; they do not make judgments.

Claude role map: ~/.claude/sdlc-engines.conf. Codex role map: ~/.codex/sdlc-openai/engines.toml. A change applies to work handed out after you save it; a session that is already open keeps the model it started with. Escalation needs your explicit request.

Setup, doctor and current evidence
CommandWhat it checks
./doctorInstalled files, routing and local dependencies.
./doctor --workspace /path/to/workspaceProject setup and the saved results of earlier runs; it does not rerun tests.
./doctor --project /path/to/repo --verifyFor one project: a fresh time-limited run of the checks.

Use doctor after changing settings, upgrading a client or adding a project. This page explains the workflow; doctor reports live status. Installing this framework starts no service.

Words used here
Gate
A point where work stops until a check passes or a person says yes. Gate 1 approves the plan; Gate 2 approves the release.
Hook
A small script the AI tool runs automatically at set moments, for example before a commit is saved. It runs the checks; it does not make judgments.
Spec
The written plan for a change: requirements (what it must do), design (how) and tasks (the steps).
REQ-ID
A short label such as REQ-LOGIN-001 on each requirement. The test that proves it carries the same label, so you can see what is covered.
Worktree
A separate working copy of the project, so the AI can build on a branch without touching the copy you are using.
RCA
Root cause analysis: find why a bug happened, fix the cause, add a test so it cannot quietly come back, and look for the same mistake elsewhere.
The roles
Judge, build, verify and read: the four jobs the AI work is split into. Each is a job, not a fixed model.
Engine map
A small settings file that says which AI model fills each role. You can edit it; the change applies to new work.
Project-specific routines

The framework handles common work; projects may add their own routines. For current project evidence, run ./doctor --workspace /path/to/workspace. Select a card for its local commands.

Trainers: open this file in a text editor, find the PROJECTS list and copy the example block to add your own projects.
